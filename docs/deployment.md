# Deployment Guide

Pursuit backend deploys to **Render** (web service + PostGIS database) via GitHub Actions.

## Architecture

```
GitHub push/tag
  -> GitHub Actions (lint + test)
    -> Render deploy hook (Docker build + migration + gunicorn)
```

| Environment | Trigger | Auto-deploy | Settings module |
|---|---|---|---|
| **Staging** | Push to `main` | Yes | `pursuit_backend.settings.staging` |
| **Production** | Tag `v*` or manual `workflow_dispatch` | No | `pursuit_backend.settings.production` |

Each environment has its own isolated PostGIS database defined in `render.yaml`.

## How Deploys Work

### Staging

1. Push or merge to `main`.
2. GitHub Actions runs `lint` and `test` jobs.
3. On success, the `deploy-staging` job calls the Render deploy hook.
4. Render pulls the latest `main`, builds the Docker image, runs migrations via `entrypoint.sh`, and starts gunicorn.
5. The workflow waits, then verifies `/api/health/` returns `200`.

### Production

1. Tag a release: `git tag v0.1.0 && git push origin v0.1.0`
   — **or** trigger manually via GitHub Actions > "Run workflow".
2. GitHub Actions runs `lint` and `test` jobs.
3. On success, the `deploy-production` job calls the Render deploy hook.
4. Same Docker build + migrate + gunicorn flow as staging.
5. Health check verifies the deployment.

## GitHub Secrets Required

Configure these in **GitHub > Settings > Secrets and variables > Actions**:

| Secret | Description |
|---|---|
| `RENDER_STAGING_DEPLOY_HOOK` | Render deploy hook URL for the staging service |
| `RENDER_PRODUCTION_DEPLOY_HOOK` | Render deploy hook URL for the production service |
| `RENDER_STAGING_URL` | Staging base URL, e.g. `https://pursuit-backend-staging.onrender.com` |
| `RENDER_PRODUCTION_URL` | Production base URL, e.g. `https://pursuit-backend-prod.onrender.com` |

To get the deploy hook URL: Render Dashboard > Service > Settings > Deploy Hook.

## Render Environment Variables

These are configured in the **Render dashboard** (not GitHub Secrets):

| Variable | Notes |
|---|---|
| `DATABASE_URL` | Auto-set when you link a PostgreSQL instance |
| `SECRET_KEY` | Auto-generated by `render.yaml` blueprint |
| `JWT_SECRET_KEY` | Auto-generated by `render.yaml` blueprint |
| `ALLOWED_HOSTS` | Set manually, e.g. `pursuit-backend-staging.onrender.com` |
| `CORS_ALLOWED_ORIGINS` | Set manually, e.g. `https://app.pursuit.com` |
| `DJANGO_SETTINGS_MODULE` | Set by `render.yaml` — do not change |

## Rollback

### Via Render Dashboard

1. Go to the Render Dashboard > select the service.
2. Click **Events** or **Deploys**.
3. Find the last known-good deploy.
4. Click **Redeploy** on that commit.

### Via Git (re-deploy a previous tag)

```bash
# Production: re-tag the known-good commit
git tag -d v0.1.1               # delete bad tag locally
git push origin :refs/tags/v0.1.1  # delete from remote
# The previous tag (v0.1.0) is still deployed — or manually trigger
# workflow_dispatch from main at the desired commit.
```

### Via GitHub Actions

Use **Actions > CI & Deploy > Run workflow** to trigger a manual production deploy from `main` at any time.

## Health Check Verification

Both services expose a health check endpoint:

```bash
curl https://pursuit-backend-staging.onrender.com/api/health/
# {"status": "healthy"}
```

The deploy workflow automatically verifies this after each deployment.

## Render Blueprint

The `render.yaml` file at the project root defines all infrastructure:

- `pursuit-backend-staging` — web service (Docker, auto-deploy from `main`)
- `pursuit-backend-prod` — web service (Docker, manual deploy)
- `pursuit-db-staging` — PostGIS-enabled PostgreSQL for staging (free tier)
- `pursuit-db-prod` — PostGIS-enabled PostgreSQL for production (free tier)

To set up from scratch: Render Dashboard > New > Blueprint > connect this repo.

## Troubleshooting

| Issue | Fix |
|---|---|
| Deploy hook returns non-200 | Verify the hook URL in GitHub Secrets matches Render |
| Health check fails | Check Render logs for migration errors or missing env vars |
| `Production settings validation failed` | Ensure `SECRET_KEY`, `JWT_SECRET_KEY`, and `ALLOWED_HOSTS` are set in Render |
| Database connection errors | Verify `DATABASE_URL` is set (auto-linked via blueprint) |
| Static files 404 | `collectstatic` runs in the Dockerfile — check build logs |
